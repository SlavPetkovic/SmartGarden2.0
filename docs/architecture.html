SmartGarden Blueprint

A clean-slate design for a sensor-driven irrigation and lighting system on a Raspberry Pi 5 — three plants on a kitchen windowsill today, dozens of beds across a garden later, without a rewrite in between. This document is the contract the build is written against.

01Scope

What Phase 1 delivers, and — more usefully — what it deliberately does not.

Phase 1 is a complete, running system: it reads three real sensors, stores everything, decides when to water and light, acts on those decisions, and presents all of it on a phone. The irrigation hardware does not exist yet, so Phase 1 ships simulated actuator drivers alongside real sensor drivers. The whole loop is exercisable today; when relays and valves arrive it is a config change, not a code change.

  • SCOPE-1The system runs end-to-end on real sensor hardware with simulated actuators, and switches to real actuators by editing devices.toml only. simulated in P1
  • SCOPE-2All decision logic is testable without a Raspberry Pi, without I2C and without a database.
  • SCOPE-3Adding a new sensor type requires a new driver file and a config entry — no changes to storage, API or UI code. This is the primary design constraint.
  • SCOPE-4The data written in Phase 1 is the training set for Phase 2. Schema decisions are made accordingly.

02Platform

Target hardware and the one library choice that is not negotiable.

Blocking constraint

RPi.GPIO does not work on the Raspberry Pi 5. The Pi 5 moved its GPIO behind the RP1 south bridge, and the legacy library cannot address it. All GPIO goes through gpiozero with the lgpio pin factory.

03Architecture

Two processes, one database, and a deliberate absence of coupling between them.

The control loop and the web server are separate systemd units. A crash in the dashboard, or a deploy of a UI change, must never interrupt watering. They communicate only through SQLite: the loop writes observations and reads a command queue; the web process writes commands and settings and reads everything else.

  • ARCH-1Control and web run as independent systemd units. Neither imports code that would make it depend on the other running.
  • ARCH-2The control loop is the only writer of hardware state. The web process never touches GPIO or I2C.
  • ARCH-3Manual actions from the UI are queued as commands rows and executed by the loop, so every action passes the same safety guards as an automatic one.
  • ARCH-4The core package is pure: it imports nothing from drivers, storage or web, and performs no I/O.
  • ARCH-5SQLite opens in WAL mode with an explicit busy_timeout, so a long analytics read cannot fail a control-loop write.
  • ARCH-6Ingest endpoints accept readings from external nodes in the same normalised shape the local bus produces, so a remote sensor is indistinguishable downstream.

04Data model

Measurements are channels, not columns. This is what makes SCOPE-3 achievable.

The previous system stored one column per measurement, so adding a sensor meant editing a dataclass, a schema, an insert, an API payload and the dashboard JavaScript. Here a driver declares its channels and everything downstream is generated from that declaration.

  • DATA-1Measurements are stored narrow: one row per (channel, timestamp, value). No measurement ever becomes a table column.
  • DATA-2Each driver declares its channels — key, unit, precision, plausible range — and channel rows are reconciled from that declaration at startup.
  • DATA-3Rules and the UI reference channels by role (soil_moisture, air_temp, light, …), never by sensor or driver identity.
  • DATA-4Every node carries stale_after_s; a node with no reading inside that window is reported offline rather than silently assumed current.
  • DATA-5A plant carries its own care profile — target moisture band, DLI target, notes — and inherits zone defaults where unset.
  • DATA-6Readings carry a quality flag so a retried or out-of-range sample is recorded rather than discarded, and can be excluded from model fitting later.

05Storage

Narrow rows, tiered retention, and a migration path that does not involve hand-editing DDL.

TierResolutionRetainedPurpose
Raw10 s / 60 s7 daysLive view, short-window trends, incident forensics.
Minute1 min90 daysCharts beyond a day; the primary Phase 2 training resolution.
Quarter-hour15 minindefiniteSeason-over-season comparison. Roughly 35 MB per channel-year.

Sample rates are per channel, not global: light and air change quickly and are read every 10 seconds; soil moisture moves slowly and is read every 60. At roughly ten channels that is on the order of 1–2 GB of raw data per year before rollup — immaterial on a 256 GB NVMe, but enough to make unbounded raw retention a slow-query problem within a couple of years.

  • STOR-1Schema changes are numbered SQL migration files applied in order and recorded in a schema_migrations table. There is exactly one source of schema truth.
  • STOR-2A rollup job runs on a schedule, is idempotent, and is safe to re-run over an already-rolled window.
  • STOR-3Rollups store min, max, mean and sample count — not just mean — so variability survives downsampling.
  • STOR-4Nightly VACUUM INTO backup to a separate path on the NVMe, with a retention count and a documented restore command that is tested at least once.
  • STOR-5An export command produces joined CSV or Parquet — readings, decisions, actuations, outcomes — suitable for direct use in a notebook.
  • STOR-6All timestamps stored UTC, ISO-8601, timezone-aware. Local time exists only at display and at watering-window evaluation.

06Sensing

Drivers are plugins. Failure is expected and recorded rather than thrown away.

# config/sensors.toml — adding a sensor is this, plus a driver file

[[sensor]]
node    = "pi-local"
driver  = "seesaw_soil"
address = "0x36"
mux_channel = 0
interval_s  = 60
roles   = { moisture = "soil_moisture", temperature = "soil_temp" }
zone    = "windowsill"
plant   = "monstera"
  • SENS-1A driver implements channels() and read() and registers itself by name. Nothing else in the codebase enumerates driver types.
  • SENS-2A failed read is retried with backoff, then recorded as a failure against that sensor. One dead sensor must not stall the loop or block other sensors.
  • SENS-3Readings outside a channel's declared plausible range are stored flagged, not silently dropped and not silently trusted.
  • SENS-4TCA9548A multiplexer support is in the driver layer from the start, since Seesaw offers only four addresses and the target is dozens of plants.
  • SENS-5VEML7700 gain and integration time are configured explicitly and recorded, because lux is meaningless without them.
  • SENS-6BME680 gas resistance is read and stored but not used for control. It requires burn-in and is not yet calibrated to anything meaningful.
  • SENS-7Simulated drivers model soil drying as a function of VPD and light rather than emitting noise, so the control loop can be exercised realistically without hardware.
  • SENS-8A doctor command scans the I2C bus, walks multiplexer channels, and reports which configured sensors answered and which did not.
Calibration required before automation

The Seesaw sensor reports roughly 200–2000 capacitance counts. The previous system's stress threshold of 350 is close to “probe in open air”. Thresholds must be derived from several days of logged readings on the actual plant in its actual soil, not carried over. Until then, run with automation disabled and observe.

07Control

Fixed thresholds in Phase 1. Legible decisions, so Phase 2 has something to improve on.

Phase 1 control is deliberately simple: threshold irrigation with hysteresis, and light supplemented against a daily light integral target. No learning, no adaptation. Every decision is written to the database with the inputs it saw and a human-readable reason, which is both the debugging surface and the Phase 2 baseline.

Irrigation

  • CTRL-1Irrigate when the zone's soil-moisture role falls below the plant's low threshold; stop at the high threshold. The band is explicit — a single threshold causes oscillation.
  • CTRL-2Pulse duration in Phase 1 is a fixed per-zone configured value. Dose calculation from a learned absorption model is Phase 2.
  • CTRL-3After a pulse, a settling period is enforced during which moisture is recorded but no new irrigation decision is made. This both prevents overwatering and produces clean pre/post pairs for CTRL-9.

Lighting by daily light integral

Rather than switching on below a lux threshold, the system integrates measured light through the day into mol·m⁻²·d⁻¹ and supplements only enough to reach each plant's DLI target before the photoperiod closes. This is how horticulture actually measures light, it uses the VEML7700 data you already collect, and it does not run the lamp on a bright afternoon merely because a cloud passed.

  • CTRL-4Accumulate measured illuminance into a daily light integral per plant, reset at local midnight.
  • CTRL-5Supplement only within the configured photoperiod, only when the projected end-of-day DLI falls short of target.
  • CTRL-6The lux-to-PPFD conversion factor is configurable per fixture and its assumption is documented, since it is spectrum-dependent and approximate.
  • CTRL-7Lighting switches carry a minimum dwell time so passing cloud cannot chatter the relay.

Decision logging

  • CTRL-8Every tick writes a decision row: inputs considered, action chosen, and a reason string legible without reading source code.
  • CTRL-9Every actuation records pre-state, commanded duration, actual duration, and post-state after the settling window — the labelled pairs Phase 2 needs.
  • CTRL-10Vapour pressure deficit is computed from temperature and humidity and stored as a derived channel on every tick. It is the physical driver of transpiration and the strongest feature available for Phase 2.

08Safety

Three independent layers, because the failure mode is water on your floor while you are away.

  • SAFE-1Guards are pure functions that can only veto or reduce. No guard may lengthen or create an actuation. This is enforced by test.
  • SAFE-2Every device declares max_on_seconds, enforced inside the driver itself regardless of what the caller requests.
  • SAFE-3A watchdog thread independent of the control loop tracks on-time per device and forces off anything past its limit.
  • SAFE-4SIGTERM and atexit handlers drive every output to its safe state, and ExecStopPost runs a standalone script that does the same without importing the application.
  • SAFE-5Outputs initialise to off at startup and are asserted off before the first control decision.
  • SAFE-6Per-zone daily water budget and per-hour pulse cap, both evaluated in the zone's local timezone with correct DST handling.
  • SAFE-7A global pause switch, settable from the UI, stops all automation while continuing to record. Manual commands are also blocked while paused.
  • SAFE-8Relay polarity (active_low) is configurable per device, defaults to the safe interpretation, and is verified by the doctor command before automation is enabled.

  • API-2Channel and role metadata is served from an endpoint, so a new sensor appears in the UI without a front-end change.

  • UI-4Manual water and light actions are available per zone, clearly labelled as still subject to safety guards.
  • UI-5Temperature unit is a display toggle; all storage and computation remain SI.
  • UI-6Charts mark irrigation events on the time axis, so cause and effect are readable in one glance.

  • OPS-1Two systemd units with restart-on-failure, journald logging, and ExecStopPost safety hooks on the control unit.
  • OPS-2Structured logging via the standard logging module throughout. No print statements in application code.
  • OPS-3Configuration is validated at startup with clear, specific errors. An invalid config fails loudly rather than falling back to a default that waters something.
  • OPS-4Notifications go through a pluggable notifier: in-app always on, ntfy and Telegram enabled by environment variable.
  • OPS-5Alert conditions at minimum: node offline, sensor read failures over threshold, moisture critical, watering blocked by budget, and irrigation with no measurable moisture response.
  • OPS-6Alerts are debounced and rate-limited per condition. An alerting system that cries wolf gets muted, which is worse than none.
  • OPS-7docs/ contains a parts list with rough prices, relay and valve-manifold wiring diagrams, mains and pump safety notes, and an operational runbook.
  • OPS-8Pure-logic tests run without hardware or a Pi. Guards, rules, DLI accumulation, VPD, rollups and unit conversion all carry tests.

11Phase 2 hooks

One target chosen: forecasting how fast soil dries. Everything here exists to make that possible later.

The chosen Phase 2 direction is moisture decay forecasting — predicting time-to-stress from current moisture, VPD, light and soil temperature, rather than extrapolating a straight line through the last two readings. Nothing in Phase 1 implements it. What Phase 1 must do is produce data of the right shape, because that cannot be backfilled.

  • ML-1VPD is computed and stored on every tick as a first-class derived channel, not recomputed at fit time from possibly-rolled-up inputs.
  • ML-2Irrigation events carry explicit start and end boundaries plus a settling window, so drying segments between waterings can be extracted unambiguously.
  • ML-3Pre-state, commanded duration, actual duration and post-state are recorded per actuation — the labelled examples a dose–response model would need if that direction is picked up later.
  • ML-4The quality flag from DATA-6 makes suspect samples excludable at fit time without deleting them.
  • ML-5Minute-resolution data is retained 90 days, which is the training resolution and horizon a first model needs.
  • ML-6The decision table records what the system believed at decision time, so a future model can be evaluated against the rule baseline on identical history.
Sequencing

No model is fitted until there are several weeks of data across varied conditions. Until then the rule baseline is the system, and its decision log is the benchmark any model has to beat.
